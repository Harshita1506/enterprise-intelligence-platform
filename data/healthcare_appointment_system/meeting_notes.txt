Meeting Type: Sprint 8 Architecture & Blocker Review
Date: September 14, 2025
Duration: 60 minutes
Attendees: Sarah Johnson (Product Manager), Alex Kumar (Frontend Lead), Priya Patel (Backend Lead), Michael Chen (Integration Engineer), Emily Davis (QA/Compliance Lead), Rohan Sharma (Chief Medical Information Officer / Sponsor)

1. Meeting Summary
The primary objective of Sprint 8 was to finalize the bidirectional integration with the CareSync EHR, specifically focusing on the POST /api/v1/fhir/Appointment (write) endpoint. While the frontend patient portal and Twilio SMS notification engine are progressing ahead of schedule, severe scalability issues have been discovered with the on-premise CareSync system. Under simulated load, the legacy EHR database is locking, resulting in API timeouts and failed appointment bookings.

2. Key Decisions Made

Asynchronous Booking Architecture: Based on Michael Chen's load testing results, Rohan Sharma approved a significant architectural pivot. Instead of synchronous, real-time writes to the EHR, we will implement RabbitMQ as an asynchronous message broker. Patient bookings will be immediately confirmed on the CareFlow frontend and queued in RabbitMQ, then slowly trickled into the CareSync EHR at a rate it can tolerate.

Twilio Short Code Deferral: Emily Davis noted that the compliance approval for a dedicated healthcare SMS short code via Twilio is taking longer than expected. Sarah Johnson decided to launch with a standard 10-digit long code (10DLC) for SMS reminders to prevent timeline slippage, migrating to the short code post-launch.

EHR Vendor Escalation: It was decided that our internal teams have exhausted their optimization options for the CareSync database. Rohan Sharma will formally escalate the locking issue to the CareSync VP of Engineering.

3. Discussion Details & Blockers

CareSync Concurrency Failure: Priya Patel presented Datadog APM metrics showing that when more than 15 concurrent booking requests hit the CareSync FHIR API, the system throws HTTP 503 (Service Unavailable) or HTTP 500 (Internal Server Error) due to legacy database row-level locking. This makes a synchronous booking flow impossible during peak morning hours.

Patient Experience Concern: Alex Kumar raised a concern that if we use RabbitMQ, there is a small chance a patient books a slot that is theoretically "available" in the cache, but fails to write to the EHR if a call-center agent booked it simultaneously.

Resolution to Double-Booking: The team agreed to implement a "pending confirmation" UI state. The frontend will show "Booking Pending," and the Twilio engine will text the patient a final confirmation once the RabbitMQ worker successfully writes the record to CareSync.
